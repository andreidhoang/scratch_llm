FOUNDATIONS
What attention costs at one million tokens
YOUR GUIDE
Let's get started.

The block we assembled in the previous chapter processed 10 tokens, and its attention sublayer built a 10 × 10 table of scores without any visible effort. Kimi K3's config declares max_position_embeddings of 1,048,576 — the model is specified to handle sequences a hundred thousand times longer than our toy run. In this chapter we take the standard attention we just built and price it at that length, with actual arithmetic rather than big-O notation. Two separate costs come out of the exercise, and they are the two problems the entire K3 attention stack exists to solve.

The accounting needs a concrete model to price, so we set one up: a hypothetical fully-dense 93-layer transformer using K3's own attention dimensions — 96 heads of 128 dimensions per layer, standard causal attention in every layer, bfloat16 activations. To be clear about what this is: K3 itself is not built this way, and by the end of the chapter the numbers will show why nobody would build it this way. The hypothetical is the baseline block from last chapter, scaled up and stacked 93 high, which is exactly the thing K3's designers had to walk away from.

Cost one: the score matrix

Standard attention compares every query against every key. For a sequence of length T, each head materializes a T × T matrix of scores — that is the scores = q @ k.transpose(-2, -1) line from our implementation. The matrix grows with the square of the sequence length, and we can watch it grow by allocating it for real at increasing T:

import torch

torch.manual_seed(3)
d = 64

for T in [1024, 2048, 4096, 8192]:
    q = torch.randn(T, d)
    k = torch.randn(T, d)
    scores = q @ k.T / d**0.5              # the T-by-T matrix, actually allocated
    mb = scores.element_size() * scores.nelement() / 2**20
    print(f"T={T:>5}: scores {tuple(scores.shape)} -> {mb:6.1f} MB")
T= 1024: scores (1024, 1024) ->    4.0 MB
T= 2048: scores (2048, 2048) ->   16.0 MB
T= 4096: scores (4096, 4096) ->   64.0 MB
T= 8192: scores (8192, 8192) ->  256.0 MB

Each doubling of T quadruples the matrix: 4, 16, 64, 256 MB. That is one head, in a toy model, at sequence lengths that would have been called long a few years ago. Extrapolate the same fp32 arithmetic to one million tokens and a single head's score matrix in bf16 would occupy 2.0 TiB — a number so far past any GPU's memory that it makes the point on its own.1
1 No production system actually materializes the full matrix. FlashAttention-style kernels compute it in tiles that never leave on-chip memory, which removes the storage problem. However, tiling does not remove the arithmetic: every one of the T² score entries must still be computed. The memory cost is avoidable; the compute cost is not.

The compute is the harder floor. Scoring T queries against T keys costs 2 · T² · head_dim floating-point operations per head (multiply and add for each of the T² · head_dim products), and applying the resulting weights to the values costs the same again. For the full hypothetical model:

n_heads, head_dim, n_layers = 96, 128, 93
T = 1048576
flops_qk = 2 * T * T * head_dim * n_heads * n_layers   # scores
flops_av = flops_qk                                    # weights @ V, same shape of work
print(f"{flops_qk + flops_av:.3e}")
5.026e+18

Five exaFLOPs — 5 × 10¹⁸ operations — for the attention arithmetic of one forward pass over one million tokens, before a single MLP or projection is counted. As the figure below summarizes, the quadratic term does not creep up on you; between 128K and 1M context it grows 64-fold.

The T × T score matrix at growing sequence lengths. The measured 4 → 16 → 64 → 256 MB progression extrapolates to terabytes per head at K3's specified 1M context.
Cost two: the KV cache

The quadratic cost dominates the prefill — the first pass over a long prompt. During generation, a different cost takes over, and for serving it is the one that hurts more.

When the model generates token by token, each new token needs attention scores against every previous position. Recomputing all previous keys and values at every step would be ruinously wasteful, so every serving system stores them: the KV cache, holding each layer's key and value vectors for every position seen so far. The cache is what turns generation from quadratic-per-token into linear-per-token; its price is memory. Each new token appends, at every layer, one key and one value vector per head:

n_heads, head_dim, n_layers = 96, 128, 93
bytes_per_scalar = 2                                   # bf16
per_token_per_layer = n_heads * head_dim * 2 * bytes_per_scalar   # K and V
per_token = per_token_per_layer * n_layers
print(per_token_per_layer, "bytes per layer per token")
print(f"{per_token / 2**20:.2f} MiB per token, all 93 layers")

for T in [131072, 1048576]:
    total = per_token * T
    print(f"T = {T:>8}: {total / 1e9:8.1f} GB")
49152 bytes per layer per token
4.36 MiB per token, all 93 layers
T =   131072:    599.1 GB
T =  1048576:   4793.2 GB

Walk through the arithmetic once by hand, because these four numbers carry the rest of the book. Per layer, per token: 96 heads × 128 dimensions × 2 tensors (a key and a value) × 2 bytes of bf16 = 49,152 bytes, or 48 KiB. Multiply by 93 layers: 4.36 MiB of cache for every single token in context. At a 128K context (131,072 tokens) the cache reaches 599.1 GB; at the full million-token context, 4,793.2 GB — call it 4.8 terabytes.2
2 We report powers-of-ten GB here (10⁹ bytes), matching how GPU memory is marketed. In binary units the 1M-token figure is 4.36 TiB. Either way it exceeds any single accelerator by an order of magnitude.

These numbers are for one sequence. A serving system running a batch of 8 such requests would need 8 caches. The figure below assembles the ledger in one place.

The cache arithmetic for the hypothetical dense model: 48 KiB per layer per token compounds to 4.8 TB at a million tokens.
What 4.8 TB means in hardware

To calibrate these totals against real machines: K3's recommended single-node deployment is 8× B300, with 288 GB of HBM per GPU — about 2.3 TB for the node. That node holds the entire 2.8-trillion-parameter model in its quantized form. Now compare:

print(f"{per_token * 1048576 / 2.3e12:.2f}")
2.08

The KV cache of our hypothetical dense model, for a single million-token sequence, would be 2.08× the total memory of the eight-GPU node that serves all of K3. The 128K case is no more comfortable: 599.1 GB overflows a 288 GB GPU more than twice over before any weights are loaded. A dense 93-layer model with these attention dimensions cannot serve long contexts at any batch size worth having; the cache, not the compute, is the binding constraint.

There is a speed consequence hiding in the same numbers. To produce each new token, attention must read the entire cache — every cached key for scoring, every cached value for averaging. At 1M context that is a 4.8 TB read per generated token, which turns generation into a memory-bandwidth problem: the GPUs spend their time streaming cache, not doing arithmetic. Long-context decoding on a dense model is slow even when it fits, and the figure below shows why.3
3 This is why decode throughput degrades as conversations grow, on every dense-attention model, independent of how fast the GPU's tensor cores are. Prefill is compute-bound (the T² term); decode is bandwidth-bound (the cache read). A long-context architecture has to fix both regimes.

The two escape routes

Every number above traces back to one design decision in the standard block: attention keeps everything. The score matrix is T × T because every query touches every key; the cache is linear in T with an enormous constant because every layer must retain every position's key and value forever, at full width.

The two costs of standard attention and K3's two answers: a state that never grows on most layers, a compressed cache on the rest.

As the figure lays out, K3 attacks the two costs with two different mechanisms, and the split is the architecture's signature. On 69 of its 93 layers, K3 uses Kimi Delta Attention, whose memory is a fixed-size state — a matrix updated once per token, the same size at token one million as at token one. No score matrix, no growing cache; Moonshot attributes to this design up to 6.3× faster decoding at million-token context. On the remaining 24 layers, K3 keeps genuine full attention — some tasks need exact retrieval over the whole context, a point we return to in Part 03 — but caches a compressed 512-dimensional latent per token (kv_lora_rank 512) instead of the full 96 × 128 × 2 keys-and-values, using multi-head latent attention. The 24 full-attention layers appear every 4th layer, a roughly 3:1 interleave.

Both mechanisms will be built in this book, in full, at mini-K3 scale. However, the fixed-size state comes first, because it is the more radical departure: it abandons the "keep everything" contract entirely and replaces lookup with memory. The next chapter takes the softmax attention we have been pricing and rewrites it — with one substitution in the formula — into a form where the whole past compresses into a single small matrix. That rewrite, linear attention, is the foundation Kimi Delta Attention stands on, and its failure modes are as instructive as its cost savings.
